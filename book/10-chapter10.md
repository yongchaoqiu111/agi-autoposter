## 10.1 什么是"可控执行"

可控执行不是"不出错"，而是：

> 出错的时候，你能知道、能追溯、能补救、能防止扩散。

可控执行包含五个维度：

| 维度 | 说明 |
|------|------|
| 可观测 | 所有状态都能看到 |
| 可追溯 | 每个操作都能找到责任人 |
| 可干预 | 出问题时能手动介入 |
| 可恢复 | 失败后能自动/手动恢复 |
| 可防御 | 异常被隔离，不扩散 |

这五个维度，缺一不可。

## 10.2 任务队列：有序是可控的前提

### 10.2.1 为什么需要队列

如果没有队列：

- 任务同时涌入，系统瞬间过载
- 无法控制任务顺序
- 无法限制并发数
- 无法实现"同平台间隔"

**队列的本质：把"无序的请求"变成"有序的执行"。**

### 10.2.2 队列的设计原则

| 原则 | 说明 |
|------|------|
| FIFO | 先来先服务，公平 |
| 优先级队列 | 重要任务可以插队 |
| 平台隔离 | 每个平台独立队列 |
| 持久化 | 队列不丢任务 |

### 10.2.3 平台隔离队列

每个平台有自己独立的任务队列：

```text
抖音队列：   [任务1] [任务4] [任务7] → 串行执行
Facebook队列：[任务2] [任务5] → 串行执行
TikTok队列： [任务3] [任务6] [任务8] → 串行执行
```

好处：

- 同平台任务自动排队，不会触发限流
- 不同平台可以并发执行
- 一个平台卡住，不影响其他平台

## 10.3 并发控制：不能太多，也不能太少

### 10.3.1 为什么要控制并发

| 并发数过低 | 并发数过高 |
|-----------|-----------|
| 任务排队久 | 系统过载 |
| 资源浪费 | 触发平台限流 |
| 处理慢 | 容易出错 |

**目标：找到适合你场景的"最优并发数"。**

### 10.3.2 并发数的设定原则

| 场景 | 推荐并发数 | 理由 |
|------|-----------|------|
| 单账号 | 1-3 | 防止平台封号 |
| 多账号同一平台 | 3-5 | 各账号独立，可适当并发 |
| 多平台混跑 | 5-10 | 平台间无冲突 |
| 高合规场景 | 1 | 宁可慢，不可错 |

### 10.3.3 动态调整机制

系统可以基于历史数据自动调整并发数：

```text
if 最近失败率 > 10%:
    并发数减半
elif 队列长度 > 100:
    并发数增加 20%
```

**原则：保守调整，一次只改一点。**

## 10.4 超时强杀：不能让任务永远卡住

### 10.4.1 为什么需要超时

一个任务可能永久卡住的原因：

- Worker 进程假死
- 网络请求无限等待
- 平台响应极慢
- 代码死循环

如果没有超时机制，这个任务会永远占用资源。

### 10.4.2 超时时间的设定

| 平台类型 | 推荐超时 | 理由 |
|----------|---------|------|
| API 调用 | 10-30 秒 | 正常 API 响应很快 |
| 浏览器自动化 | 60-120 秒 | 页面加载慢 |
| 文件上传 | 120-300 秒 | 大文件需要时间 |
| 未知任务 | 60 秒（默认） | 保守估计 |

**原则：超时时间 = 正常执行时间的 3 倍。**

### 10.4.3 强杀机制

超时后不能只是"标记失败"，必须强制终止进程：

```python
try:
    result = await asyncio.wait_for(worker_task, timeout=WORKER_TIMEOUT)
except asyncio.TimeoutError:
    # 强制终止
    worker_process.kill()
    await worker_process.wait()
    task.status = "timeout"
    task.result = f"Worker timeout after {WORKER_TIMEOUT}s"
```

为什么必须强杀？

- 只标记超时，进程可能还在后台运行
- 残留进程会消耗内存、CPU、网络连接
- 长期累积会导致系统资源耗尽

## 10.5 失败重试：不能一次失败就放弃

### 10.5.1 重试策略

| 策略 | 说明 |
|------|------|
| 立即重试 | 适合瞬时错误（如网络抖动） |
| 延迟重试 | 适合限流、临时不可用 |
| 指数退避 | 第1次等1秒，第2次等2秒，第4秒... |
| 上限次数 | 最多重试 N 次，防止无限重试 |

### 10.5.2 什么错误应该重试

| 错误类型 | 是否重试 | 理由 |
|----------|---------|------|
| 网络超时 | ✅ 是 | 可能是临时问题 |
| 平台限流 | ✅ 是（延迟重试） | 等一会儿可能恢复 |
| 登录失效 | ❌ 否 | 需要人工介入 |
| 内容违规 | ❌ 否 | 重试也没用 |
| 参数错误 | ❌ 否 | 代码问题，不是临时问题 |

### 10.5.3 重试的代码实现

```python
def execute_with_retry(task, max_retries=3):
    for attempt in range(max_retries + 1):
        try:
            result = execute(task)
            if result.success:
                return result
        except Exception as e:
            if attempt == max_retries:
                raise
            wait_time = 2 ** attempt  # 指数退避
            time.sleep(wait_time)
```

## 10.6 限流与间隔：保护账号不被封

### 10.6.1 为什么需要限流

平台会检测发帖频率。太快会被 Ban。

| 平台 | 建议间隔 |
|------|---------|
| 抖音 | 5-10 分钟 |
| Facebook | 10-30 分钟 |
| X (Twitter) | 2-5 分钟 |
| Instagram | 10-20 分钟 |

### 10.6.2 间隔控制的实现

```python
# 每个平台记录上次发帖时间
last_post_time = {
    "douyin": None,
    "facebook": None,
    "tiktok": None,
}

def can_post(platform):
    last = last_post_time.get(platform)
    if last is None:
        return True
    interval = PLATFORM_INTERVAL.get(platform, 60)  # 默认60秒
    return (time.now() - last) >= interval

def post(platform, content):
    if not can_post(platform):
        # 加入等待队列，而不是直接拒绝
        wait_until_next_slot(platform)
    # 执行发帖
    result = do_post(platform, content)
    last_post_time[platform] = time.now()
    return result
```

### 10.6.3 动态间隔

可以根据账号状态动态调整间隔：

```text
if 账号信用好:
    间隔 = 5 分钟
elif 账号刚解封:
    间隔 = 30 分钟
else:
    间隔 = 10 分钟（默认）
```

## 10.7 状态管理：每个任务都要有"户口"

### 10.7.1 任务的生命周期

```text
pending → running → success
                ↘ failed
                ↘ timeout
                ↘ retry → pending（回到起点）
```

### 10.7.2 任务需要记录的信息

| 字段 | 说明 | 用途 |
|------|------|------|
| task_id | 唯一标识 | 追溯 |
| status | 当前状态 | 监控 |
| platform | 目标平台 | 分类 |
| content_id | 内容 ID | 关联内容层 |
| created_at | 创建时间 | 审计 |
| started_at | 开始时间 | 性能分析 |
| completed_at | 完成时间 | 性能分析 |
| result | 执行结果 | 反馈学习 |
| error_msg | 错误信息 | 排查问题 |
| retry_count | 已重试次数 | 控制重试 |
| worker_pid | 进程 ID | 超时强杀 |

### 10.7.3 状态存储

| 阶段 | 存储方式 | 说明 |
|------|---------|------|
| Demo | 内存 dict | 简单，但重启丢失 |
| 生产 | Redis + 数据库 | Redis 存实时状态，数据库持久化 |

## 10.8 日志与审计：出了事能找到原因

### 10.8.1 日志分级

| 级别 | 用途 |
|------|------|
| DEBUG | 开发调试 |
| INFO | 正常操作记录 |
| WARNING | 异常但可自动恢复 |
| ERROR | 需要人工关注 |
| CRITICAL | 系统严重故障 |

### 10.8.2 必须记录的关键事件

- 任务创建
- 任务开始
- 任务成功
- 任务失败（含错误原因）
- 任务超时
- 任务重试
- 参数校验失败
- 平台限流触发

### 10.8.3 审计日志的格式

```json
{
  "timestamp": "2025-05-05T10:00:00Z",
  "level": "INFO",
  "event": "task_created",
  "task_id": "task_0001",
  "platform": "douyin",
  "operator": "scheduler-001",
  "trace_id": "abc-123-def"
}
```

**原则：审计日志应该是不可变的——只能追加，不能修改，不能删除。**

## 10.9 异常隔离：一个任务失败不影响其他

### 10.9.1 隔离原则

失败是常态，但失败不能扩散。

### 10.9.2 隔离机制

| 层级 | 隔离方式 |
|------|---------|
| 任务级 | 每个任务独立进程/协程 |
| 平台级 | 每个平台独立队列 |
| 账号级 | 每个账号独立 Worker |
| 分身级 | 分身之间不共享状态 |

### 10.9.3 失败扩散的防护

```python
# ❌ 错误做法：一个任务失败导致队列清空
try:
    for task in queue:
        execute(task)
except Exception:
    queue.clear()  # 千万别这么做！

# ✅ 正确做法：只跳过失败的任务
for task in queue:
    try:
        execute(task)
    except Exception as e:
        log_error(task, e)
        continue  # 继续下一个
```

## 10.10 人工介入机制：系统不能完全无人值守

### 10.10.1 什么时候需要人工介入

| 场景 | 说明 |
|------|------|
| 首次配置 | 需要人填写平台账号、API Key |
| 登录失效 | 平台 Token 过期 |
| 持续失败 | 同一任务失败超过 N 次 |
| 异常模式 | 系统检测到异常行为 |
| 探索模式授权 | 开启新功能需要人确认 |

### 10.10.2 介入方式

| 方式 | 适用场景 |
|------|---------|
| 邮件/短信告警 | 非紧急，可以等 |
| 企业微信/钉钉通知 | 需要关注 |
| Web 管理界面操作 | 需要手动干预 |
| API 调用 | 可通过其他系统自动处理 |

### 10.10.3 告警阈值示例

```text
if 成功率 < 90% in last 1 hour:
    发送告警（邮件）

if 同一任务失败 > 3 次:
    发送告警（钉钉），暂停该任务

if 队列长度 > 100:
    发送告警（短信），人工介入
```

## 10.11 可控执行的完整检查清单

部署前，确认以下问题都有答案：

| 问题 | 检查项 |
|------|-------|
| 能看到吗？ | 是否有监控看板？日志是否完整？ |
| 能追溯吗？ | 每个任务是否有唯一 ID？是否能查到历史？ |
| 能干预吗？ | 能否暂停任务？能否强制终止？ |
| 能恢复吗？ | 失败后是否自动重试？重试次数是否有限制？ |
| 能防御吗？ | 失败是否隔离？超时是否强杀？ |

## 10.12 本章小结

可控执行不是一句口号，而是一系列可落地的机制：

| 机制 | 作用 |
|------|------|
| 任务队列 | 有序执行，避免混乱 |
| 并发控制 | 防止过载，合理利用资源 |
| 超时强杀 | 阻止任务永远卡死 |
| 失败重试 | 提高成功率，减少人工干预 |
| 限流间隔 | 保护账号不被平台封禁 |
| 状态管理 | 每个任务可追溯 |
| 日志审计 | 出了问题能找到原因 |
| 异常隔离 | 一个失败不影响其他 |
| 人工介入 | 系统不能完全无人值守 |

**一句话总结：**

> 可控执行 = 队列 + 并发控制 + 超时 + 重试 + 限流 + 状态 + 日志 + 隔离 + 人工介入。
>
> 九个机制，缺一不可。
