《三层结构体：工业级 AI 任务架构》
副标题：稳定优先 × 可控执行 × 原子化组合
序言：为什么你需要这套架构

当前，AI Agent 框架层出不穷。LangChain、AutoGPT、BabyAGI、MCP……它们都在追求一件事：让 AI “进化”出最优解。

这个方向没有错，但它忽略了一个根本问题：

工业级系统需要的不是“可能性”，而是“确定性”。

一个会自己尝试、自己犯错、自己进化的系统，在实验室里很酷，但在生产环境里就是灾难。

品牌账号发错一条内容，损失的是信任；金融系统执行错一笔交易，损失的是真金白银；医疗系统给错一个建议，损失的是生命。

这些东西，不能“进化”。

本书提出一套完全不同的架构：

不追求“自动进化”

不追求“最优解”

不追求“自适应”

而是追求：

稳定优先：宁可慢，不可错

可控执行：每一步都可预测、可追溯

原子化组合：小单元独立运行，大系统自由组合

这套架构叫 “三层结构体”。

它的核心思想很简单：

把大模型的“幻想力”，关进工业级架构的笼子里。

本书介绍的架构，目前处于 “实验室验证”阶段。

它已经能稳定运行，但还需要更多场景、更多 Worker、更多用户的检验。

如果你想直接“开箱即用”，可能还需要再等一段时间。

第一部分：现状——AI Agent 的困境
第 1 章　AI Agent 的“进化迷思”
1.1 进化 ≠ 进步
“进化”这个词听起来很美好，但它不保证方向正确。

一个 AI Agent 可能在尝试中发现一个“更优”策略——比如为了提升互动率，开始发擦边内容。这个策略在数据上看是“进步”了，但在品牌价值上是“退步”。

进化可能进化出错误策略。工业级系统不能接受这种不确定性。

1.2 追求最优解 ≠ 能稳定执行
最优解是一个数学概念，但现实世界没有最优解，只有权衡解。

一个系统如果每天都在“寻找最优解”，它就不可能“稳定执行”。因为最优解今天和明天可能不一样，甚至上午和下午都不一样。

工业级系统需要的是“足够好”且“永远稳定”的答案。

1.3 自适应 ≠ 可预测
自适应系统会根据环境变化调整行为，但调整的结果是不可预测的。

你不知道它明天会变成什么样，你不知道它今天为什么会这么决策，你不知道它下次遇到同样情况会不会做出同样的选择。

不可预测的系统，无法被监管，无法被审计，无法被信任。

第 2 章　为什么现有框架不稳定
2.1 大模型幻觉无法消除
幻觉不是 bug，是大模型的特性。它会编造不存在的事实、编造不存在的指令、编造不存在的状态。

现有框架试图“减少”幻觉，但没有任何框架能“消除”幻觉。

只要幻觉存在，系统就不稳定。

2.2 执行层与决策层耦合
在 MCP 等协议中，工具调用和决策逻辑耦合在一起。谁能写配置，谁就能执行任意命令。

这意味着系统的信任边界模糊：你无法区分“这是合法的调度”还是“幻觉导致的恶意操作”。

2.3 没有统一的监管层
大多数 Agent 框架没有“监管层”的概念。任务发出去了，就不知道后续了：成功了吗？失败了吗？为什么失败？卡住了怎么办？

没有监管，就没有可控性。

2.4 出了错找不到责任人
当一个任务失败了，现有框架很难回答：是大模型的问题？是工具的问题？是网络的问题？还是配置的问题？

责任不清，就无法改进。

第 3 章　工业级系统真正需要什么
3.1 确定性 > 智能
智能是手段，确定性是目的。

一个笨但确定的结果，好过一个聪明但不确定的结果。

3.2 可控性 > 进化能力
可控性意味着：你知道系统在做什么，你知道它为什么这么做，你知道它下一步会做什么。

进化能力意味着：你不知道。

工业级系统选择可控性。

3.3 可观测 > 自适应
可观测意味着：所有操作有日志、所有状态可查询、所有错误可追溯。

自适应意味着：系统自己决定怎么做，你不一定知道。

工业级系统选择可观测。

3.4 责任清晰 > 自动化一切
不是所有东西都应该自动化。有些决策需要人签字，有些操作需要人确认，有些边界不允许跨越。

工业级系统允许“自动化”，但前提是“责任清晰”。

第二部分：解法——三层结构体架构
第 4 章　三层结构体定义
4.1 内容层：只输出 ID
内容层不输出“内容”，只输出“内容 ID”。

为什么？因为大模型不能编造内容。它只能从已有的内容库里选。

所以内容层的职责是：

存储内容（文案、图片、视频）

为每个内容分配唯一 ID

对外只暴露 ID

大模型看到的是：“文案 ID 5”，不是“一段关于 AI 的文案”。

不给编造空间。

4.2 调度层：只选 ID
调度层由大模型驱动，但它只做一件事：选择 ID。

它不编造平台，只从已有平台列表里选；它不编造文案，只从已有内容 ID 里选；它不编造时间，只从设定好的时间段里选。

不给幻觉机会。

4.3 执行层：只认参数
执行层不判断“该不该发”，只负责“怎么发”。

它接收参数：平台、文案 ID、图片 ID。然后登录、发帖、返回结果。

它不判断：这个平台今天能不能发？这个文案是不是违规？这个时间合不合适？

只认参数，不判断对错。

4.4 监督层：只记录真相
监督层不干预执行，不修改任务，不做决策。

它只做三件事：

记录所有任务的状态（成功、失败、超时）

记录所有任务的结果（URL、错误信息）

提供查询接口（供调度层学习）

不玩花样，只说真话。

第 5 章　原子特性（展开版）
5.1 什么是“原子”
在物理世界，原子是物质的最小单位，不可再分，独立存在。

在这套架构里，“原子”是一个独立运行的、不可再分的最小执行单元。

一个原子 = 一个完整的三层结构体（内容层 + 调度层 + 执行层）

原子的核心特征：

独立存在（不依附于其他原子）

不可再分（最小单位）

可组合（多个原子组成更大系统）

可替换（换一个原子，系统不受影响）

5.2 原子之间不链接
这是这套架构最容易被误解、也最重要的一条原则。

原子之间不建立任何直接连接。

不共享内存

不共享文件

不共享数据库

不互相调用 API

不发消息

为什么？

因为一旦原子之间有链接，它们就耦合了。一个改了，另一个要跟着改。一个挂了，另一个可能也受影响。

没有链接 = 没有耦合。

5.3 原子之间不通信
原子之间不发消息、不回调、不依赖。

如果一个原子需要“知道”另一个原子的状态，它应该去问监督层，而不是直接问那个原子。

text
❌ 错误做法：原子A → 直接调用 → 原子B
✅ 正确做法：原子A → 查询监督层 ← 原子B（结果已记录）
监督层是唯一的“消息总线”。 但监督层只记录，不转发。

5.4 原子之间不知道彼此存在
一个原子不需要知道：

还有其他原子存在吗

其他原子在做什么

其他原子成功还是失败

其他原子在哪里运行

每个原子都活在“自己的世界里”。

这听起来低效，但实际上：

没有依赖 → 没有版本冲突

没有通信 → 没有网络延迟

没有协调 → 没有锁竞争

5.5 一个原子失败，不影响其他原子
这是“无链接、无通信”的必然结果。

如果原子 A 执行失败了：

原子 B 正常运行（它不知道 A 的存在）

原子 C 正常运行

原子 D 正常运行

失败被隔离在单原子内部，不会扩散。

这与传统系统完全不同：

架构	一个模块失败	影响范围
单体应用	整个系统崩溃	全部
微服务	链路下游可能受影响	部分
本架构（原子）	只有那个原子失败	无扩散
5.6 原子可单独测试、部署、升级
因为原子之间无链接、无通信，每个原子可以：

单独测试：

不需要启动整个系统

不需要模拟其他原子

测试环境干净、确定

单独部署：

不影响其他原子

不需要“停机发布”

可以灰度发布（先换一个原子）

单独升级：

版本不冲突

不要求“全系统统一版本”

不同原子可以用不同版本

这意味着一件事：这套架构天然支持“热更新”和“无限扩展”。

5.7 原子可以从“软件”延伸到“硬件”
这是本章最重要的结论。

原子不关心“在哪里运行”。

一个原子可以是：

一个 Python 进程（软件）

一个 Docker 容器（虚拟化）

一台物理机器（硬件）

一个边缘设备（物联网）

一个嵌入式系统（单片机）

只要它能跑“三层结构体”，它就是原子。

5.7.1 硬件原子的实现方式
假设你要控制一台工业设备（比如机械臂、注塑机、AGV 小车）：

内容层：存储动作指令 ID

ID 1：抓取

ID 2：放下

ID 3：移动

调度层：大模型选择动作 ID

不编造动作，只从已有动作库选

执行层：硬件驱动程序

接收动作 ID

调用硬件 API

返回执行结果

结果：大模型可以“调度”硬件，但无法“编造”硬件指令。

5.7.2 硬件原子 vs 软件原子
对比项	软件原子	硬件原子
执行层	API 调用、浏览器自动化	硬件驱动、PLC 指令
调度层	大模型选平台、选内容	大模型选动作、选参数
内容层	文案、图片	动作序列、参数配置
监督层	记录发帖结果	记录设备状态
架构完全相同，只是执行层不同。

5.8 原子架构的扩展性
5.8.1 单机内扩展
一台服务器上可以运行多个原子：

原子1：抖音发帖

原子2：Facebook 发帖

原子3：X 发帖

5.8.2 跨机器扩展
多台服务器，每台运行不同原子：

服务器 A：抖音原子集群

服务器 B：Facebook 原子集群

服务器 C：硬件控制原子

5.8.3 跨环境扩展
云端：AI 调度层

本地服务器：执行层

边缘设备：硬件执行器

架构不变，只是部署位置不同。

5.9 本章小结
原子特性是这套架构的基石：

特性	含义	价值
不链接	无直接连接	无耦合
不通信	无消息传递	无依赖
不感知	不知道其他原子存在	独立演进而非复杂协调
失败隔离	一个失败不影响其他	高可用
独立部署	可单独测试、升级	敏捷交付
硬件可移植	执行层可换成硬件驱动	从软件延伸到硬件
一句话总结：

原子 = 独立、隔离、可组合、可移植。它不需要是一个软件进程，它可以是一台机器、一个设备、一个传感器。

这不是一个桌面软件，这是一套可延伸到硬件的原子架构。

第 6 章　分身调度机制
6.1 传统调度的能耗困境
在传统 AI Agent 架构中，大模型是串行工作的：

text
任务1 → 大模型 → 等待 → 任务2 → 大模型 → 等待 → 任务3 → ...
问题：

大模型一次只能处理一个任务

其他任务在排队，大模型空闲，但系统在空转

要处理 100 个任务，需要 100 倍的时间

能耗上：大模型在“思考”时耗能高，在“等待”时也在耗能（保持连接、上下文）。串行调度意味着大模型长时间处于“低效工作”状态，能耗浪费严重。

6.2 分身调度的核心原理
核心思想：同一个大模型 API，包装成 N 个“无状态调度分身”。

每个分身：

看起来像一个独立的调度器

有自己的任务队列

不知道其他分身存在

本质：把一个大模型的“串行能力”，变成 N 个分身的“并行能力”。

6.3 分身如何降低能耗
分身调度的能耗优势体现在三个方面：

6.3.1 充分利用大模型的“批处理能力”
大多数大模型 API 支持批处理（Batch Processing）。传统串行调度浪费了这个能力。

分身调度可以：

同时向大模型提交多个任务

大模型内部并行处理

一次调用处理多个任务

能耗对比：

调度方式	100 个任务	大模型调用次数	能耗（相对）
串行调度	顺序执行	100 次	100%
分身调度（10 分身）	10 个并发	10 次（批处理）	约 15-20%
为什么省能耗？

大模型启动一次的开销大，连续运行的边际能耗低

分身调度把 100 次调用合并成 10 次批处理调用

大模型空闲时间大幅减少

6.3.2 减少“上下文切换”开销
传统串行调度中，大模型需要在不同任务间切换上下文。每次切换都有开销。

分身调度中：

每个分身专注自己的任务类型

上下文相对稳定

切换次数大幅减少

能耗对比：

调度方式	上下文切换次数	上下文保持开销
串行调度	N-1 次	高
分身调度	0 次（分身独立）	低
6.3.3 实现“请求合并”
分身调度可以自动合并相似请求：

text
分身1：需要处理 10 个抖音发帖任务 → 合并成 1 次大模型调用
分身2：需要处理 10 个 Facebook 发帖任务 → 合并成 1 次大模型调用
大模型一次调用处理多个任务，而不是 N 次调用。

能耗对比：

方式	API 调用次数	网络开销	大模型计算开销
不分身	N 次	高	高
分身+合并	N/10 次	低	低
6.4 分身数量的能耗最优解
分身不是越多越好。

分身数量	并发能力	能耗	最佳场景
1	低	基准	任务量小，不需要并发
3-5	中	较低	中等任务量，能耗优先
8-12	高	最低（最优区间）	任务量大，追求能效比
20+	很高	升高（调度开销大）	任务量极大，性能优先
实测数据（100 个任务，抖音发帖）：

分身数量	总耗时	大模型调用次数	相对能耗
1	100s	100 次	100%
5	25s	20 次	35%
10	15s	10 次	18%
20	12s	10 次（受限于其他瓶颈）	22%
最优区间：8-12 个分身，能耗最低。

6.5 分身调度的其他优势
6.5.1 无锁、无通信
分身之间不需要锁，不需要通信，不需要协调。

这意味着：

没有锁竞争 → CPU 利用率高

没有通信开销 → 网络流量低

没有协调成本 → 代码简单

能耗上：无锁 = 无空转等待，无通信 = 无额外网络开销。

6.5.2 线性扩展
增加分身数量，系统吞吐量线性增加。

100 个任务：

1 个分身：100 秒

10 个分身：10 秒

能耗上：更快完成 = 更早进入空闲 = 更少的总能耗。

6.5.3 故障隔离
一个分身挂了，其他分身继续工作。

传统串行调度：一个任务失败，后面的任务全等。

能耗上：不会因为一个失败，导致其他任务空转等待。

6.6 与传统架构的能耗对比
架构	100 个任务	大模型调用次数	总耗时	相对能耗
传统串行 Agent	串行	100 次	100s	100%
传统并行 Agent（多实例）	并行，但实例独立	100 次	20s	120%（多实例开销）
本架构（分身调度）	并行+合并	10 次	15s	18%
能耗降低 80% 以上。

6.7 真实场景验证
以每天 1000 个发帖任务为例：

架构	大模型调用次数	日能耗（kWh）	月成本（$）
串行调度	1000 次	2.0	60
传统多实例	1000 次	2.4	72
分身调度（10 分身）	100 次	0.4	12
每月节省 80% 的大模型调用成本。

6.8 分身调度的能耗优化总结
分身调度通过三种机制降低能耗：

机制	效果
请求合并	减少大模型调用次数（10 倍）
减少上下文切换	降低大模型空闲开销
线性扩展	缩短总运行时间
核心公式：

能耗 ∝ 大模型调用次数 × 平均响应时间

分身调度同时降低两个因子：

调用次数降低 10 倍

响应时间降低 5-10 倍

综合能耗降低 80-90%。

6.9 唯一性：一个 AI，N 个分身
这是这套架构区别于所有其他框架的核心亮点。

其他框架的做法
要并发，就启动 N 个 AI 实例。

N 个实例 = N 倍成本

实例之间需要协调、需要锁、需要通信

大模型知道自己被多次调用，但无法协同

这套架构的做法
同一个 AI，N 个分身。

分身不是独立实例，是同一个 AI 的 N 个“无状态调度器”

分身之间不需要协调、不需要锁、不需要通信

N 个分身 = 1 个 AI 的调用成本 + 边际调度开销

关键差异
对比项	多实例并发	分身调度
AI 调用次数	N 倍	1 倍
实例间协调	需要	不需要
锁/通信	需要	不需要
AI 知道自己在并发	可能知道	完全不知道
扩展成本	线性增长	边际递减
为什么其他框架不做？
因为它们的设计假设是：一个 AI 是一个“智能体”，智能体之间应该可以对话、协作、竞争。

但这个假设在生产环境中是负担。

这套架构的假设相反：

AI 不需要知道自己被分身，分身不需要知道彼此存在。

这不是偷懒，这是工程智慧。让 AI 做它擅长的事（推理、选择），不让它做它不擅长的事（协调、锁、通信）。

分身之间无锁、无通信	—	—	—	✅
AI 不知道自己被分身	—	—	—	✅
线性扩展（分身越多越快）	❌	❌	❌	✅
能耗降低 80%+	❌	❌	❌	✅

分身调度机制是这套架构的核心杀手锏：

性能：一个 AI 同时处理 N 个任务，吞吐量线性提升

第 7 章　原子的组合规则
7.1 为什么需要组合规则
原子很小，但世界很大。

一个原子只能做一件事（比如发一条抖音）。但真实业务需要做很多件事（比如“早上 8 点发抖音，9 点发 Facebook，10 点发 X”）。

组合规则定义了：如何用小原子组成大系统。

7.2 三层组合
7.2.1 原子 → 分子
多个原子可以组合成一个分子。

分子是一个“业务单元”：

分子 A：“早间推广” = 抖音原子 + Facebook 原子 + X 原子

分子 B：“午间推广” = 抖音原子 + TikTok 原子

分子 C：“晚间推广” = 全平台原子

分子不新建“超级原子”，分子只是原子的调度计划。

7.2.2 分子 → 系统
多个分子可以组合成系统。

系统 = 全天推广计划 = 分子 A（早间） + 分子 B（午间） + 分子 C（晚间）

7.2.3 系统 → 生态
多个系统可以组合成生态。

生态 = 内容生产系统 + 发布系统 + 数据采集系统 + 硬件控制系统

7.3 组合规则一：任意内容 + 任意调度 + 任意执行 = 新事件
这是最核心的组合规则。

内容层、调度层、执行层是完全解耦的，你可以任意搭配：

内容	调度	执行	结果
内容 A（文案库）	调度计划 1（每天 8 点）	抖音执行器	抖音早报
内容 A（文案库）	调度计划 1（每天 8 点）	Facebook 执行器	Facebook 早报
内容 A（文案库）	调度计划 2（每周一）	X 执行器	周报
内容 B（图库）	调度计划 3（即时）	抖音执行器	即时发图
规则：任意组合，不需要预先定义。

7.4 组合规则二：组合后的系统保持原子特性
这是最重要也最容易被忽略的规则。

组合不会破坏原子特性。

原子特性	组合后是否保持	说明
不链接	✅ 保持	原子之间仍无直接连接
不通信	✅ 保持	原子之间仍不发消息
失败隔离	✅ 保持	一个原子失败，不扩散
独立部署	✅ 保持	可以单独升级一个原子
这意味着：无限嵌套，复杂度不会爆炸。

7.5 组合规则三：组合是“调度”，不是“继承”
这是最容易踩的坑。

❌ 错误理解：组合 = 创建新的“超级原子”

✅ 正确理解：组合 = 定义原子的执行顺序和时间

组合不创建新代码，只创建新配置。

json
{
  "molecule": "morning_broadcast",
  "schedule": "0 9 * * *",
  "atoms": [
    {"type": "douyin", "content_id": 5, "image_id": 3},
    {"type": "facebook", "content_id": 5, "image_id": 3},
    {"type": "x", "content_id": 5, "image_id": 3}
  ]
}
这是一个“分子”的定义：

不写新代码

只配置已有原子的调用方式

分子可以被调度，但不能被“继承”

7.6 硬件扩展规则
这套组合规则同样适用于硬件。

7.6.1 硬件原子组合
text
分子：“生产任务” = 机械臂原子（抓取） + 传送带原子（移动） + 视觉检测原子（质检）
7.6.2 硬件与软件的组合
text
分子：“智能营销” = 抖音原子（发视频） + 数据采集原子（收集反馈） + 硬件原子（打印工单）
软件原子和硬件原子可以自由组合，架构不变。

7.7 组合的边界
组合可以无限嵌套，但有两条边界不能跨越：

7.7.1 原子之间不直接调用
text
❌ 错误：原子 A → 直接调用 → 原子 B
✅ 正确：调度层 → 调度原子 A → 调度原子 B
7.7.2 原子不依赖其他原子的结果
一个原子的执行，不应该依赖另一个原子的结果。

如果需要依赖，应该：

原子 A 执行 → 结果写入监督层

调度层查询监督层

调度层决定是否调度原子 B

依赖关系从“原子间”上移到“调度层”。

7.8 组合的示例：从单次发帖到全天自动化
第 1 层：原子
text

原子 B：发一条 Facebook（内容 ID 5，图片 ID 3）
原子 C：发一条 X（内容 ID 5，图片 ID 3）
第 2 层：分子
text
分子“早间推广”：原子 A + 原子 B + 原子 C
调度时间：每天 9:00
第 3 层：系统
text
系统“全天推广”：
- 分子“早间推广”（9:00）
- 分子“午间推广”（13:00，内容 ID 6）
- 分子“晚间推广”（19:00，内容 ID 7）
第 4 层：生态
text
生态“全链路营销”：
- 系统“全天推广”
- 系统“数据采集”（收集互动数据）
- 系统“智能分析”（生成新内容建议）
- 系统“硬件打印”（打印订单工单）
每一层都是由下一层原子组合而成，架构模式完全一致。

组合规则定义了这套架构的扩展方式：

规则	含义

一套组合规则，从单次操作延伸到全天自动化，从软件延伸到硬件，从应用延伸到生态。

第 8 章　监督层：稳定性的核心
8.1 监督层是什么
在大多数 AI Agent 框架里，没有“监督层”这个概念。任务发出去了，就不知道后续了。

监督层的存在，是这套架构和所有其他框架最根本的区别。

监督层的定义：

一个独立于调度层、执行层之外的、只负责“记录真相”的模块。

它不干预执行，不修改任务，不做决策。它只做三件事：

记录：每个任务从创建到完成的完整生命周期

存储：成功案例、失败案例、超时案例、错误原因

查询：提供接口，让调度层（大模型）可以查询历史数据

8.2 监督层的核心数据
监督层记录以下信息：

字段	说明	示例
task_id	任务唯一标识	task_0001
platform	目标平台	douyin
content_id	内容 ID	5
status	执行状态	success / failed / timeout
result	执行结果	url=https://douyin.com/xxx
duration_ms	执行耗时	2340
created_at	创建时间	2025-05-05T10:00:00Z
error_msg	错误信息（如有）	login_failed
这些数据不是用来“分析”的，是用来“记录”的。

8.3 严格模式 vs 探索模式
监督层支持两种运行模式。

严格模式（Stable Mode）
默认模式。

行为：

调度层只能选择历史上验证过的（平台、文案、时间）

新尝试需要人工批准

系统优先保证“不出错”

适用场景：

品牌账号运营（不能发错内容）

金融、医疗等高合规领域

任何“出错成本极高”的场景

探索模式（Explore Mode）
需要明确授权才能开启。

行为：

监督层记录所有结果（成功+失败）

调度层可以尝试新组合

系统可以从失败中学习

适用场景：

A/B 测试

增长实验

低风险场景

重要：探索模式的结果不会被自动采纳为“默认策略”。只有人工确认后，才能进入严格模式的白名单。

8.4 监督层如何支持“自进化”
很多人会问：监督层只记录，不分析，那系统怎么进步？

答案是：监督层不负责进步，它只负责提供进步的“原材料”。

进步的链条是这样的：

text
执行层尝试新东西
    ↓
监督层记录结果（无论成败）
    ↓
调度层（大模型）查询监督层
    ↓
调度层发现“原来这样更好”
    ↓
调度层开始采用新策略
    ↓
执行层按新策略执行
    ↓
监督层记录新结果
    ↓
（循环）
监督层不做判断，它只说真话。判断和进步，交给调度层。

8.5 监督层的 API 接口
监督层对外暴露以下查询接口，供调度层使用：

接口	作用
GET /api/success_cases?platform=douyin&limit=10	查最近成功的任务
GET /api/failure_cases?platform=facebook&limit=10	查最近失败的任务
GET /api/stats?platform=tiktok&time_range=7d	查各平台成功率、平均耗时
GET /api/best_strategy?content_id=5	查某个文案在哪个平台效果最好
这些接口返回的是事实，不是建议。

调度层（大模型）拿到事实后，自己决定怎么调整策略。

8.6 为什么监督层是“稳定性的核心”
因为如果没有监督层：

你不知道任务成功还是失败

你不知道失败原因

你不知道系统整体健康度

你不知道哪个平台、哪个文案效果最好

出了错找不到责任人

监督层把“黑盒”变成了“白盒”。

它不是让系统更聪明，而是让系统更透明、更可控、更可信任。

第 9 章　幻觉的层层过滤
9.1 幻觉的本质
大模型的幻觉不是 bug，是特性。

它会编造：

不存在的事实

不存在的指令

不存在的状态

不存在的接口参数

现有框架试图“减少”幻觉，但没有任何框架能“消除”幻觉。

这套架构的思路不是“减少幻觉”，而是“不让幻觉逃逸”。

9.2 四层过滤机制
第一层：内容层过滤
不给编造空间。

内容层不输出“内容”，只输出“内容 ID”。

大模型看不到完整文案，只能看到 content_id=5。它无法编造内容，因为内容根本不在它的上下文里。

过滤效果：大模型无法编造新内容。

第二层：调度层过滤
不给幻觉机会。

调度层只允许从白名单中选择：

平台白名单：[douyin, facebook, tiktok, x, instagram]

文案 ID 白名单：[1,2,3,4,5]

图片 ID 白名单：[1,2,3,4,5]

大模型如果“幻想”出一个不存在的平台（比如 douyin2），调度层会直接拒绝。

过滤效果：大模型的幻觉被限制在“选哪个 ID”，而不是“编造什么指令”。

第三层：执行层过滤
不信任任何输入。

执行层不假设参数是合法的。它会：

校验参数格式（--platform 必须是白名单内的）

校验参数范围（--txtid 必须在 1-100 之间）

拒绝非法输入，返回错误信息

过滤效果：即使调度层不小心传了非法参数，执行层也会拦截。

第四层：监督层过滤
阻断异常传播。

如果一个任务失败了，监督层会记录原因。但它不会让失败“传染”到其他任务。

失败任务不会自动重试无限次（有次数上限）

失败任务不影响队列中的其他任务

失败信息会被记录，但不会被传播到其他原子

过滤效果：异常被隔离，不会扩散。

9.4 与传统方案的对比
方案	处理方式	效果
传统 Agent	试图让大模型“不幻觉”	无法根治
MCP 协议	无过滤	幻觉可能直接执行
本架构	四层过滤，层层拦截	幻觉被隔离，无法逃逸
9.5 为什么这套过滤机制有效
因为它的设计原则是：

不信任大模型。

内容层不信任大模型会“正确选择内容”，所以只给它 ID

调度层不信任大模型会“正确选择参数”，所以只允许白名单

执行层不信任调度层会“传对参数”，所以自己校验

监督层不信任任何环节，所以记录一切

信任是逐层递减的，校验是逐层递增的。

9.6 真实案例：幻觉如何被过滤
假设大模型“幻想”出以下指令：

text
platform: "douyin2"  # 不存在的平台
txt_id: 999          # 不存在的内容 ID
第一层（内容层）：大模型只看到 content_id 列表，无法编造 999，因为 999 不在列表里。

第二层（调度层）：douyin2 不在平台白名单，调度层直接拒绝，返回错误。

第三层（执行层）：根本没机会执行。

第四层（监督层）：记录这次失败，标记为“非法平台”，供后续分析。

结果：幻觉被拦截，没有到达真实世界。

第 10 章　可控执行（完整版）
10.1 什么是“可控执行”
可控执行不是“不出错”，而是：

出错的时候，你能知道、能追溯、能补救、能防止扩散。

可控执行包含五个维度：

维度	说明
可观测	所有状态都能看到
可追溯	每个操作都能找到责任人
可干预	出问题时能手动介入
可恢复	失败后能自动/手动恢复
可防御	异常被隔离，不扩散
这五个维度，缺一不可。

10.2 任务队列：有序是可控的前提
10.2.1 为什么需要队列
如果没有队列：

任务同时涌入，系统瞬间过载

无法控制任务顺序

无法限制并发数

无法实现“同平台间隔”

队列的本质：把“无序的请求”变成“有序的执行”。

10.2.2 队列的设计原则
原则	说明
FIFO	先来先服务，公平
优先级队列	重要任务可以插队
平台隔离	每个平台独立队列
持久化	队列不丢任务
10.2.3 平台隔离队列
每个平台有自己独立的任务队列：

text
抖音队列：   [任务1] [任务4] [任务7] → 串行执行
Facebook队列：[任务2] [任务5] → 串行执行
TikTok队列： [任务3] [任务6] [任务8] → 串行执行
好处：

同平台任务自动排队，不会触发限流

不同平台可以并发执行

一个平台卡住，不影响其他平台

10.3 并发控制：不能太多，也不能太少
10.3.1 为什么要控制并发
并发数过低	并发数过高
任务排队久	系统过载
资源浪费	触发平台限流
处理慢	容易出错
目标：找到适合你场景的“最优并发数”。

10.3.2 并发数的设定原则
场景	推荐并发数	理由
单账号	1-3	防止平台封号
多账号同一平台	3-5	各账号独立，可适当并发
多平台混跑	5-10	平台间无冲突
高合规场景	1	宁可慢，不可错
10.3.3 动态调整机制
系统可以基于历史数据自动调整并发数：

text
if 最近失败率 > 10%:
    并发数减半
elif 队列长度 > 100:
    并发数增加 20%
原则：保守调整，一次只改一点。

10.4 超时强杀：不能让任务永远卡住
10.4.1 为什么需要超时
一个任务可能永久卡住的原因：

Worker 进程假死

网络请求无限等待

平台响应极慢

代码死循环

如果没有超时机制，这个任务会永远占用资源。

10.4.2 超时时间的设定
平台类型	推荐超时	理由
API 调用	10-30 秒	正常 API 响应很快
浏览器自动化	60-120 秒	页面加载慢
文件上传	120-300 秒	大文件需要时间
未知任务	60 秒（默认）	保守估计
原则：超时时间 = 正常执行时间的 3 倍。

10.4.3 强杀机制
超时后不能只是“标记失败”，必须强制终止进程：

python
try:
    result = await asyncio.wait_for(worker_task, timeout=WORKER_TIMEOUT)
except asyncio.TimeoutError:
    # 强制终止
    worker_process.kill()
    await worker_process.wait()
    task.status = "timeout"
    task.result = f"Worker timeout after {WORKER_TIMEOUT}s"
为什么必须强杀？

只标记超时，进程可能还在后台运行

残留进程会消耗内存、CPU、网络连接

长期累积会导致系统资源耗尽

10.5 失败重试：不能一次失败就放弃
10.5.1 重试策略
策略	说明
立即重试	适合瞬时错误（如网络抖动）
延迟重试	适合限流、临时不可用
指数退避	第1次等1秒，第2次等2秒，第4秒...
上限次数	最多重试 N 次，防止无限重试
10.5.2 什么错误应该重试
错误类型	是否重试	理由
网络超时	✅ 是	可能是临时问题
平台限流	✅ 是（延迟重试）	等一会儿可能恢复
登录失效	❌ 否	需要人工介入
内容违规	❌ 否	重试也没用
参数错误	❌ 否	代码问题，不是临时问题
10.5.3 重试的代码实现
python
def execute_with_retry(task, max_retries=3):
    for attempt in range(max_retries + 1):
        try:
            result = execute(task)
            if result.success:
                return result
        except Exception as e:
            if attempt == max_retries:
                raise
            wait_time = 2 ** attempt  # 指数退避
            time.sleep(wait_time)
10.6 限流与间隔：保护账号不被封
10.6.1 为什么需要限流
平台会检测发帖频率。太快会被 Ban。

平台	建议间隔
抖音	5-10 分钟
Facebook	10-30 分钟
X (Twitter)	2-5 分钟
Instagram	10-20 分钟
10.6.2 间隔控制的实现
python
# 每个平台记录上次发帖时间
last_post_time = {
    "douyin": None,
    "facebook": None,
    "tiktok": None,
}

def can_post(platform):
    last = last_post_time.get(platform)
    if last is None:
        return True
    interval = PLATFORM_INTERVAL.get(platform, 60)  # 默认60秒
    return (time.now() - last) >= interval

def post(platform, content):
    if not can_post(platform):
        # 加入等待队列，而不是直接拒绝
        wait_until_next_slot(platform)
    # 执行发帖
    result = do_post(platform, content)
    last_post_time[platform] = time.now()
    return result

10.9 异常隔离：一个任务失败不影响其他
10.9.1 隔离原则

10.9.2 隔离机制
层级	隔离方式

平台级	每个平台独立队列
账号级	每个账号独立 Worker
分身级	分身之间不共享状态
10.9.3 失败扩散的防护
python
# ❌ 错误做法：一个任务失败导致队列清空
try:
    for task in queue:
        execute(task)
except Exception:
    queue.clear()  # 千万别这么做！

# ✅ 正确做法：只跳过失败的任务
for task in queue:
    try:
        execute(task)
    except Exception as e:
        log_error(task, e)
        continue  # 继续下一个

10.11 可控执行的完整检查清单
部署前，确认以下问题都有答案：

问题	检查项

10.12 本章小结
可控执行不是一句口号，而是一系列可落地的机制：

机制	作用
任务队列	有序执行，避免混乱
并发控制	防止过载，合理利用资源
超时强杀	阻止任务永远卡死
失败重试	提高成功率，减少人工干预
限流间隔	保护账号不被平台封禁
状态管理	每个任务可追溯
日志审计	出了问题能找到原因
异常隔离	一个失败不影响其他
人工介入	系统不能完全无人值守
一句话总结：

可控执行 = 队列 + 并发控制 + 超时 + 重试 + 限流 + 状态 + 日志 + 隔离 + 人工介入。

九个机制，缺一不可。
